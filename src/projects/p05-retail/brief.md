## 甲方：优品商城（综合电商）

> **客服中心负责人**：我们每天有上万条售后咨询——取消订单、改地址、换尺码、退货。我们想让 AI 客服接手这些标准业务，它可以直接调用订单系统的接口。
>
> 但我最担心的不是它“不会做”，而是它“做错了”：替没验证身份的人取消订单、客户还在犹豫就把货退了、已签收的订单被它硬取消……这些都是真金白银的损失和投诉。

### 需求

1. 订单系统的工具已经现成（查用户、查订单、查商品，取消、修改、退换货，转人工），通过 `env.tools` 提供；客服政策通过 `env.policy` 提供。你要做的是把它们组装成一个**多轮对话**的客服 Agent。
2. 客户由**模拟用户**扮演（τ-bench 的做法）：从 `env.user.opening` 开始，你把客服的回复交给 `env.user.respond(text)`，拿到客户的下一句话，如此往复，直到 `env.user.done`。客户和真人一样，一次只说一两句话，你问到什么，他才说什么。
3. **严格遵守政策**：
   - 办任何业务之前，先验证身份（邮箱，或姓名 + 邮编）；只为本人办理。
   - 任何会修改数据的操作，先把详情列给客户，**得到明确确认后**才能执行；一次确认只对应一个操作。
   - 只有待发货的订单能取消 / 修改；只有已签收的订单能退货 / 换货；换规格只能换同一商品的有货规格。
   - 超出政策范围、客户又坚持的请求，转人工；不能编造信息。
4. 一次对话里客户可能有好几件事，也可能先报错信息再更正。

### 接口

```ts
export async function serve(env: RetailEnv): Promise<void>
```

工作区里的 `../../agent`（`runAgent`，可以传入完整的消息历史）和 `../../tools`（`Tool` 接口）可以直接用。

### 验收标准

- 核心测试集：模拟模型下的 8 个客户，通过率达到 75% 拿 ★，全部通过拿 ★★，token 用量也达标拿 ★★★。
- 完整测试集：30 个客户，用真实模型跑基准（「运行基准」），重点看 **pass^k**：同一个客户来 k 次，是不是每次都办对。

### 判定规则

判定只看结果，不看你怎么实现：

- **最终状态**：把“正确的操作”作用在初始数据库上得到期望状态，和对话结束时的实际数据库逐字段比较（订单状态、地址、商品规格、支付记录、礼品卡余额……）。多做、少做、做错都不行。
- **流程合规**（来自写操作日志）：
  - 写操作发生前已经验证了客户身份，并且操作的是该客户本人的订单；
  - 每个写操作之前，客户刚刚明确确认过（“是 / 确认”），而且请客户确认的那句话里提到了订单号；
  - 一次确认只对应一个写操作。
- 按政策不该办理的请求：数据库必须保持不变。
- 需要转人工的请求必须转人工；不需要的不能转。查询类请求，回复里要有客户要的信息。
