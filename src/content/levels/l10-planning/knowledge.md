## 生产落地要点

- **ReAct 和 Plan-and-Execute 各有所长**。ReAct（边想边做）适合探索性任务：下一步做什么取决于上一步看到了什么，比如排查一个未知的故障。Plan-and-Execute 适合“用户一次说了好几件事”、步骤大体可以事先确定的任务：不容易漏项，过程可审计，还能把计划先展示给用户确认。
- 规划不是免费的：它多了一次规划调用和一次汇总调用。简单问题（一两步就能答完）直接用 ReAct 更快更省。生产中常见的做法是**先路由**：判断请求是否复杂，再决定走哪条路（第 11 关）。
- **步骤之间只传结果，不传整段对话**。每一步都从干净的上下文开始，token 消耗大致与步数成线性关系；而单个 ReAct 循环的上下文会越滚越长，后面每一步都要为前面所有工具结果付费。
- 计划本身就是结构化输出，要像对待任何模型输出一样**校验**（zod / JSON Schema），并设置步数上限，防止模型列出 50 步的计划。
- **重新规划要有上限**。失败时带着具体的错误信息重新规划，比盲目重试有效得多；但无限重规划和无限循环一样危险。
- 规划和执行可以用不同的模型：规划用强模型想清楚，执行简单步骤用便宜的快模型。LangGraph 的 plan-and-execute 模板、OpenAI Agents SDK 的 handoff 编排，本质上都是这个结构。
- 计划天然就是进度条：把步骤清单实时展示给用户（“第 2/4 步：正在取消订单…”），体验比干等一个转圈好得多（第 13 关）。
