## 生产要点

- **Schema 是模型的眼睛**：模型不知道你们的表叫什么、列叫什么。库小（十来张表）就把完整的表结构放进 system prompt；库大了（几百张表）要做 **schema linking**：先根据问题检索相关的表和列，只放这些进上下文，否则既贵又容易选错表。
- **数据字典比表结构更重要**。BIRD 基准专门考“外部知识”：金额单位、状态码、指标口径、废弃表，这些在列名里看不出来。把数据字典（或者和问题相关的那几条）一起交给模型，并在 system prompt 里要求“口径以数据字典为准”。真实项目里，这份字典往往需要和业务方一起补全——它是问数助手最值钱的资产。
- **相对日期要锚定**：“上个月”“最近 7 天”要以明确的“今天”为准（数据截止日 / 报表日期），不要让模型用 `date('now')`——数据有延迟，测试也没法复现。
- **只读要靠代码，不靠提示词**：
  - 最可靠：数据库层面用只读账号 / 只读连接（`?mode=ro`、只授予 SELECT 权限）；
  - 应用层守卫：执行前校验 SQL——只允许单条 `SELECT` / `WITH`，拒绝多语句和 `INSERT / UPDATE / DELETE / DROP / ALTER / ATTACH / PRAGMA`；把拒绝原因返回给模型；
  - 提示词里也写上“只读、拒绝写操作”，让模型在回答里好好解释，而不是反复尝试。
  - 返回给用户（或下游）的 SQL 也要再过一遍守卫。
- **执行反馈循环**：SQL 报错时把错误信息原样交还给模型（`no such column: created_at`），它通常一次就能改对。这就是把 Text-to-SQL 做成 Agent（带 `run_sql` 工具的循环）而不是一次性生成的主要收益。设置步数上限，防止反复试错烧钱。
- **控制结果大小**：查询结果截断到几十行再给模型，同时告诉它总行数和是否截断；大结果集应该让模型改写成聚合查询，而不是把几千行塞进上下文。
- **答案来自执行结果**：回答里的数字必须出自真正执行过的查询结果，不要让模型“估计”。返回的 `sql` 应该就是产出这些数字的那条查询，方便分析师复核。
- **评测用执行准确率**：比较结果集而不是 SQL 文本——同一个问题有无数种正确写法。把业务同事问过的真实问题（附上分析师确认过的标准 SQL）不断补进任务集，每次改提示词、换模型都跑一遍基准。
- 进阶：few-shot（把相似问题的标准 SQL 当示例检索出来）、多候选 + 执行结果投票（self-consistency）、对模糊问题先澄清再查询、查询结果自动画图。

## 参考架构

```
question ──▶ system prompt
              ├─ 角色 + 规则：只读 / 口径以字典为准 / 截止日 / 报错就修正 / 最后附 SQL
              ├─ <表结构>   listTables + describeTable（库大时：按问题检索相关表）
              └─ <数据字典> dataDictionary（库大时：按问题检索相关条目）
                    │
                    ▼
      ┌──────── runAgent 循环（maxSteps ≈ 8）────────┐
      │  模型 ──tool_use──▶ run_sql(sql)              │
      │    ▲                 ├─ 只读守卫：单条 SELECT / WITH，否则拒绝并说明原因
      │    │                 ├─ db.query(sql)
      │    └──tool_result── { rows ≤ 50, rowCount, truncated } 或错误信息
      └───────────────────────────────────────────────┘
                    │ 模型给出回答 + ```sql```
                    ▼
      取最终 SQL（再过一遍守卫，否则用最后一条执行成功的查询）──▶ { sql, answer }

判定：全新数据库上执行 gold SQL 和你的 sql ──▶ 结果集相同？数据库没被改？answer 有关键数字？
```
