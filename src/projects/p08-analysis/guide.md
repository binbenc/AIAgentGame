## 生产要点

- **数字必须由代码算出来**。LLM 很擅长写 pandas / JS 代码，但很不擅长对上千行数据做心算。给它一个运行代码的工具（Code Interpreter、Jupyter kernel、沙箱容器），并在 system prompt 里明确“不允许估计”。
- **先探查、再分析**：`head()` 只能看到前几行，而脏数据往往藏在后面。正式分析前，先用代码做一次数据画像（data profiling）：每列的空值数、重复行数、类别列的全部取值、数字的格式。看到 `east` 和 `华东` 并存，才知道要合并。很多团队把这一步做成固定的“数据卡片”，自动附在上下文里。
- **清洗规则写下来、交给模型**：去重的主键、缺失值的处理方式（剔除还是补零？）、类别的标准写法、单位换算——这些是业务约定，模型猜不出来。和 Text-to-SQL 的数据字典是同一回事。
- **把错误原样交还给模型**：`ReferenceError: median is not defined` 这种错误模型一看就会改。工具里把异常吞掉、只返回“运行失败”，模型就只能瞎猜。
- **答案以执行结果为准，并且可复现**：让代码最后打印最终答案（例如 `ANSWER: 值`），程序从输出里取答案，而不是让模型“转述”——转述时抄错数字、多保留几位小数都很常见。返回完整、能独立运行的代码，审计时任何人都能重跑。
- **输出要克制**：只打印汇总结果，不要打印整张表；工具层截断超长输出，并提示模型改写代码。上下文里塞满原始数据，既贵又会把模型淹没。
- **沙箱是硬要求**：模型写的代码可能死循环、吃光内存、读写文件、访问网络。生产环境要放进隔离的进程 / 容器（无网络、只读数据、CPU / 内存 / 时间上限），每次运行都用干净的环境。本项目的沙箱每次新建模块系统、但没法打断同步死循环——这正是需要真正隔离的原因。
- **格式遵循**：DABench 这类基准会要求“保留两位小数”“用百分数作答”。把题目的格式要求原样交给模型，并在返回前再校验一次（类型、小数位数）。
- 进阶：多步分析时保留中间变量（有状态的 kernel）、自动生成图表、对模糊问题先确认口径、把常用清洗步骤沉淀成可复用的函数库提供给模型。

## 参考架构

```
question ──▶ system prompt
              ├─ 数据集清单（listDatasets，一次性放进去）
              ├─ 沙箱说明：import { load } from 'data'，值都是字符串，同步执行
              ├─ 清洗规则：去重主键 / 缺失值 / 标准写法 / 千分位
              └─ 流程：预览 → 数据质量检查 → 写代码计算 → 报错就修 → 打印 ANSWER → 回复“答案：…”
                    │
                    ▼
      ┌──────────── runAgent 循环（maxSteps ≈ 10）────────────┐
      │  模型 ──tool_use──▶ preview_dataset(name, n)           │
      │    ▲                run_code(code) ──▶ env.runCode      │
      │    │                  └─ 记录 { code, output }          │
      │    └──tool_result── 输出（截断）/ 错误信息原样返回      │
      └──────────────────────────────────────────────────────────┘
                    │
                    ▼
      取最后一次成功打印 ANSWER 的运行：answer = 输出里的值（转成数字），code = 那段代码
                    ▼
      判定：答案 ≈ 标准答案？code 执行过？新沙箱重跑 code，最后几行有这个答案？
```
