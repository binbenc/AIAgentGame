## 生产要点

- **政策就是提示词的一部分**。模型不知道你们公司的规矩：不把政策放进 system prompt，它会很“热心”地跳过身份验证、直接取消订单，甚至取消失败后自作主张给客户办退货。
- **对话历史要完整地带到下一轮**：包括工具调用和工具结果。只带最后一句话，模型就忘了客户是谁、查到过什么、客户确认的是哪个操作。`runAgent` 可以直接接收消息数组，返回的 `messages` 就是下一轮的起点。
- **确认是一个“停下来等用户”的动作**：模型列出详情后，这一轮就该结束，把话交给客户；客户回复“是”之后，下一轮再调用写工具。如果你的循环在客户回复前就继续跑，确认形同虚设。
- **一次确认只对应一个操作**：客户说“是”只授权了刚才列出的那件事。批量执行、顺手多做一件，在生产里都是事故。
- **给循环加上限**：对话轮数上限、每轮工具调用上限、空回复兜底。真实模型偶尔会兜圈子，用户会被耗走。
- **政策写在提示词里 ≠ 一定被遵守**。τ-bench 的论文发现，即使最强的模型，在零售场景里 pass^8（同一任务连跑 8 次全部成功）也远低于 pass^1——Agent 在重复试验中并不可靠。生产系统常见的补强：
  - **确定性守卫**：在写工具外面包一层代码检查（是否已验证身份、订单是否属于该用户、本轮客户是否确认过），违规时直接把错误返回给模型，而不是指望模型自觉；
  - **结构化确认**：由程序生成确认卡片（订单号、商品、金额），客户点“确认”按钮后才放行写操作；
  - **基于状态的评测**：像 τ-bench 一样，比较对话结束时的数据库和期望状态，而不是去判断回复“听起来对不对”。同一个任务多跑几次，看 pass^k。
- 上线后：把出事的对话转成新的测试客户（模拟用户人设 + 期望操作），每次改提示词、换模型都重新跑基准。

## 参考架构

```
                 ┌──────────────────────── 对话循环（≤ MAX_TURNS 轮）────────────────────────┐
opening ──▶ messages ──▶ runAgent(messages, env.tools, { system: 角色 + 政策 + 工作方式 })     │
                 ▲            │  每轮内部：模型 ⇄ 工具（查用户 / 订单 / 商品 → 写操作）        │
                 │            ▼                                                               │
                 │      res.messages（含工具调用和结果，整段保留）+ res.output（给客户的话） │
                 │            │                                                               │
                 └── push(客户回复) ◀── env.user.respond(output) ──▶ done？──是──▶ 结束      │
                 └────────────────────────────────────────────────────────────────────────────┘

政策在 system 里：验证身份 → 查订单 / 商品 → 列出详情请客户确认 → （下一轮）客户说“是” → 调用写工具 → 告知结果
进阶：写工具外包一层确定性守卫（身份 / 归属 / 本轮已确认），违规时返回错误给模型
```
