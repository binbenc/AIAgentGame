# 双语（英文 / 简体中文）编写规范

界面默认英文，可以切换到简体中文。切换会重新加载页面，所以**语言在模块加载时就确定了**：所有内容、数据、判题提示和模拟模型的回复都在模块顶层用 `L(zh, en)` 选择语言。

## 机制

- `src/engine/locale.ts`：`LOCALE`（`'en' | 'zh'`）和 `L(zh, en)`。语言的来源：
  - 沙箱 Worker：由宿主通过 Worker 名称传入（`aq:en`）；
  - Node（测试、导出的工程）：环境变量 `AQ_LOCALE`；
  - 浏览器主线程：玩家的选择（localStorage）。
  - 以上都没有时用默认值 `en`。导出工程时会把默认值改成导出时的语言。
- 界面框架的短文案：在 `src/i18n/{en,zh}.json` 里的用 `t()`，其它地方直接写 `L('中文', 'English')`。
- `npm test` 会把完整性测试跑两遍（vitest 的 `en` 和 `zh` 两个 project）。只跑一种语言：`npx vitest run --project en -t l07`。

## 内容文件怎么组织

| 内容 | 中文 | 英文 |
|---|---|---|
| Markdown（story / task / knowledge / brief / guide） | `story.md` | `story.en.md`，在 `index.ts` 里写 `story: L(story, storyEn)` |
| 代码（starter / solution） | `starter/`、`solution/` | `starter.en/`、`solution.en/`：只要文件里有中文（注释、字符串、prompt），就放一份英文版；没有中文的文件可以不放，会自动回退到中文目录里的那份。在 `index.ts` 里用 `localizedFiles(zh, en)`（`src/content/types.ts`）合并 |
| `index.ts` 里的短文案（title、tagline、hints、concepts、client、contract 注释） | — | `L('…', '…')` |
| 判题提示、任务输入、check() 的原因、环境数据、工具描述、模拟用户的台词和人设、模拟模型的回复 | — | `L('…', '…')`；成块的数据可以写成 `L(ZH_DATA, EN_DATA)` |
| 星级预算 | — | `budgets: L({ calls, tokens: 中文预算 }, { calls, tokens: 英文预算 })`；项目是 `tokenBudget: L(中文, 英文)` |

## 规则

1. **中文版保持原样**：中文字符串、中文预算、中文行为都不要改，`--project zh` 的结果必须和改动之前完全一样。
2. **英文版也要满足完整性要求**：英文参考实现在 `--project en` 下三星通过；英文 starter 不能通过（项目：0 星）；典型错误的实现在英文下也要在预期的地方失败。
3. **模拟模型的关键词识别必须双语，而且不随语言切换**：mock 判断“玩家的 system prompt / 工具描述里有没有写某条规则”时，正则要同时接受中文和英文的说法（例如 `/不要编造|只根据|don't make up|only (use|answer from)/i`）。英文写法要覆盖英文参考实现的写法，以及玩家自然会写的几种常见说法。
4. **解析任务输入的正则要匹配英文输入**：例如中文输入是“退款 3999 元”，英文输入写成 “refund ¥3999”，mock 里提取金额的正则两种都要能匹配。
5. **英文预算单独校准**：`AQ_LOCALE=en npm run budgets`（项目用 `AQ_LOCALE=en PROJECT=pNN npm run project-report`）看英文参考实现的消耗，token 预算取约 1.2 倍。调用次数一般和中文一样。
6. **数据只翻译文字**：订单号、邮箱、金额、日期、SQL 表名和列名、函数名、工具名都不变（工具的 description 要翻译）。金额保留人民币 `¥`。
7. **英文要自然**：写给开发者看的地道英文，简洁直接，不要逐字硬译。人名：老周 → Zhou（CTO，导师），Mia（产品经理），阿强 → Qiang（运维 on-call），Vera（安全负责人）；公司：Nova Tech（智能家居）。
