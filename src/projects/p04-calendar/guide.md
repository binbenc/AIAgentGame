## 生产要点

- **时区换算交给代码，不交给模型**。模型脑子里的时差是“训练数据里的常识”，它不知道下周伦敦要切冬令时。用 `Intl.DateTimeFormat({ timeZone })` 在工具里把每个人的工作时间、忙闲换算好，直接给模型一个“共同空闲时段”的列表，让它挑。日历类 Agent 的事故，十有八九出在时间换算上。
- **工具里的时间一律用带时区的 UTC ISO 字符串**（`2026-10-22T08:30:00Z`）。工具说明里写清楚格式，参数校验里拒绝不带时区的时间，并在报错里告诉模型该怎么改。给人看的时候，再附上各自的当地时间和 UTC 偏移（“伦敦 09:30，UTC+1”）。
- **告诉模型“现在”**：今天是几号、星期几、请求人在哪个时区。“明天”“下周一”“这周五”全靠它；再附一张未来两三周的日期表（日期 + 星期），模型算星期几经常出错。
- **告诉模型“我是谁”**：请求人的姓名、邮箱、时区。不然它不知道“我也参加”指的是谁。
- **规范进 system prompt，确认是一个停下来的动作**：先列方案（时间、参会人、会议室），这一轮就结束，把话交给请求人；对方确认后，下一轮再调用写操作。冲突和歧义同理：给选项，不替人做决定。
- **对话历史要完整地带到下一轮**（包括工具调用和结果）：请求人在第一句话里说的“周五下午不开会”，第三轮还得记得。
- **工具要能表达意图**：改期用 `update_event`（同一个会议 id），而不是“新建 + 忘了删”；取消要能带上“通知参会人”。没有合适的工具，模型就只能用错误的工具凑。
- **找不到就说找不到**：三地没有共同工作时间时，正确的做法是解释并给出替代方案（分开开、轮流迁就），而不是订一个有人凌晨两点要参加的会。
- 上线后：用真实的预订请求做回归集，基于最终日历状态打分（AppWorld 的做法），每次改提示词、换模型都跑一遍；特别关注夏令时切换前后的那几周。

                 ▲          system = 今天（日期 + 星期 + 时区）+ 日期表 + 请求人是谁 + env.rules + 工作方式     │
                 │          tools：                                                                          │

                 │            list_rooms / list_events                                                       │
                 │            create_event / update_event / cancel_event（只收带时区的 ISO，否则报错）         │
                 │                     │                                                                     │
                 └── push(对方回复) ◀── env.user.respond(output) ──▶ done？──是──▶ 结束                        │
