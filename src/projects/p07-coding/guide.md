## 生产要点

- **工具设计就是 Agent 的“用户界面”**（SWE-agent 论文里的 ACI，Agent-Computer Interface）：工具少而精、名字和描述一看就懂；输出带行号、有长度上限；出错时说清楚**为什么错、下一步该怎么做**（“old_str 没找到，注意缩进，先 read_file”比 “Error” 有用得多）。
- **str_replace 优于整文件重写**：让模型重写整个文件，它会漏掉没看到的部分、偷懒写“其余代码不变”，文件越大越危险，也越费 token。片段替换要做两个校验：old_str 必须**逐字存在**，并且**唯一**。
- **先找到再动手**：给模型搜索（grep）和读文件的能力。issue 里提到的文件不一定是 bug 所在；先搜函数名，再读完整的文件。
- **永远跑测试**：改完必须跑已有测试。很多修复“修好了 issue，却弄坏了别的”，只有测试能发现。更进一步：先写一个复现脚本 / 测试，确认它失败，修完再确认它通过。
- **不准改测试**：在 system prompt 里明确禁止，**并且**在工具层拒绝写 `*.test.ts`——只靠提示词约束是不够的，模型被测试卡住时很容易“走捷径”。
- **最小 diff**：只改必要的行，不顺手重构、不改格式。review 的人看得懂，回归的风险也小。
- **沙箱执行不可信代码**：Agent 写出来的代码可能有死循环、删文件、访问网络。生产环境要在容器里跑（只读挂载、无网络、CPU/内存/时间上限），每次运行用干净的环境。本项目的测试运行器每次都新建模块系统，但同步死循环仍会卡住——这正是需要真正沙箱的原因。
- **成本**：编码 Agent 的上下文会越滚越长（每一步都带着之前读过的所有文件）。控制步数上限（maxSteps），工具输出截断，只读需要的文件；mini-swe-agent 用约 100 行代码 + 一个 bash 工具就在 SWE-bench 上拿到了很高的分数——简单的循环 + 好的反馈，胜过复杂的框架。

## 参考架构

```
issue ──▶ system prompt（流程：复现 → 定位 → 最小修改 → 跑测试 → 不改测试）
            │
            ▼
      ┌──────────── runAgent 循环（maxSteps ≈ 25）────────────┐
      │  模型 ──tool_use──▶ search_code / list_files / read_file │
      │    ▲                str_replace（唯一匹配校验，拒绝改测试）│
      │    └──tool_result── write_file（只用于新建文件）          │
      │                     run_tests（失败详情 + 汇总，截断）    │
      └──────────────────────────────────────────────────────────┘
            │ 模型不再调用工具
            ▼
      判定器：最终文件 + 原始测试 + 隐藏测试 ──▶ FAIL_TO_PASS ✓ 且 PASS_TO_PASS ✓
```
