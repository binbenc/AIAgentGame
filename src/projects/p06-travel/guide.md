## 生产要点

- **让模型做它擅长的，把能算的交给代码**。TravelPlanner 论文里，GPT-4 一类的模型自己查数据、自己规划，最终通过率不到 1%：主要败在算账、核对营业时间这类“需要计算或交叉核对”的约束上。查数据、算钱、查星期几、对营业时间，都是几行确定性代码就能做对的事。
- **先把需求变成结构化约束**（`TripRequest`，第 2 关的结构化输出 + zod 校验）。后面的检索、过滤、校验都基于它；规划时把这份约束清单**原样放进提示词**，别指望模型从一大段对话里自己把每条偏好都记住。
- **缩小动作空间**：硬性偏好（不坐飞机、带宠物、无障碍、房型、最少入住晚数）直接在数据层过滤掉。模型看不到的选项，它就不会选错；上下文也更短、更便宜。
- **规划 → 校验 → 修改**（第 15 关的 evaluator-optimizer）：但评审**不要用模型**——它和规划者一样算不清账，总会说“看起来不错”。写一个确定性的校验器，把违规清单（第几天、哪个 id、违反了什么、差多少钱）逐条发回给模型，让它改；设一个修改次数上限，返回问题最少的一稿。
- **校验器要覆盖全部规则**，包括已经在过滤里处理过的偏好（纵深防御）：过滤逻辑哪天改坏了，校验器还能兜住。
- **不可行要尽早、如实地说**：用代码算一个可行性下界（每一程最便宜的交通 + 每一站最便宜的合规酒店 + 必需的餐饮门票）。下界都超预算、某一程没有合规交通、某一站没有合规酒店——直接返回 `feasible: false` 和原因，不用调模型。
- **id 只认产品库里的**：渲染给模型的数据一行一个选项、id 放在最前面；校验时不在可选项里的 id 一律当作错误。日期旁边写上星期几，营业时间、闭馆日原样给出，模型改稿时才有依据。
- **工作流还是 Agent？** 这道题的数据需求是可以从结构化约束推出来的（哪几程交通、哪几个城市），用代码一次并行查齐，比让模型在工具循环里一个个查要省得多——工具循环每一步都要重发全部历史。基准模式下两种都试试，看 token 差多少。
- 上线后：把客户投诉的行程补进任务集；产品库更新后自动重新跑基准；记录每道题修改了几轮，修改轮数变多往往说明提示词或数据渲染出了问题。
