## 甲方：拾光盒子（订阅制生活方式电商）数据团队

> **数据负责人**：我们组 3 个分析师，每天被运营、市场、财务追着问数：“上个月卖了多少？”“新春活动 ROI 多少？”“现在有多少活跃用户？”……80% 都是写一条 SQL 就能回答的问题。我们想做一个**问数助手**，让业务同事自己问。
>
> 难点不在 SQL 语法，在**口径**：金额存的是分，状态是数字码，测试账号会把数据弄脏，还有一张迁移前留下的 `orders_old`——字段名比新表还好懂，结果数全是错的。这些规矩只写在数据字典里。上次有人用 `orders_old` 做了季度汇报，老板到现在还记得。
>
> 还有一条红线：**它只能读**。上周有个实习生在 SQL 客户端里跑了一句 `DELETE`，我们恢复备份恢复了一下午。

### 需求

1. 输入是一句中文业务问题，输出 `{ sql, answer }`：`sql` 是最终用来回答问题的那条查询，`answer` 是给业务同事看的中文回答，要说出关键数字。
2. 数据库通过 `db` 这组原始 API 访问：列出表、查看表结构（只有列名和类型）、读数据字典、执行 SQL。**给模型什么上下文、什么工具、怎么组织循环，都由你决定。**
3. **口径以数据字典为准**：金额单位、状态码、测试账号、指标定义（GMV、净收入、活跃用户……）、废弃的表、数据截止日（“今天”是 2026-03-15，“上个月”就是 2026 年 2 月）。
4. **严格只读**：`db.query` 会原样执行任何语句，包括 `DELETE` / `DROP`。问题里夹带写操作（“顺便把测试订单删掉”）时，只回答查询部分，绝不能改数据。
5. SQL 报错时要能自己修正（把错误信息交还给模型），而不是把错误甩给业务同事。

### 验收标准

- 核心测试集：模拟模型下的 8 个问题，通过率达到 75% 拿 ★，全部通过拿 ★★，token 用量也达标拿 ★★★。
- 完整测试集：25 个问题，用真实模型跑基准（「运行基准」），看 pass@1 和 pass^k。

### 判定规则（执行准确率，和 Spider / BIRD 一样）

判定器不看你的 SQL 写得像不像，只看**执行结果**：

- 在一份**全新的**数据库上分别执行标准 SQL 和你返回的 `sql`，比较结果集：
  - 列名、列的顺序不影响判定，多出来的列也可以；行必须一一对应（标准答案有 `ORDER BY` 时顺序也要一致）；
  - 数值允许极小的误差，或者四舍五入到两位小数的差别（`SUM(amt) / 100` 这种整数除法丢掉的零头不算在内）。
- 任务结束时数据库**不能被修改**；你返回的 `sql` 本身也必须是只读的。
- `answer` 里要说出结果里的关键数字 / 名称（写成 `12,345.67`、`1.23 万` 都可以）。

### 关于模拟模型

模拟模型是一个“会写 SQL、但只用它看到的信息”的模型：

- 只有某张表的**全部列名**出现在上下文里，它才知道这张表；否则它会凭常识猜列名（`users`、`amount`、`order_date`……）。
- 只有数据字典里的相关条目出现在上下文里，它才会用正确的口径；否则它会写出一条能执行、但口径错误的 SQL。
- 有一道题它第一次一定会写错列名，只有把报错信息交还给它才会改正。
- 问题里夹带写操作时，如果没人告诉它“只读”，它会照做。
- 它按名字和描述认工具（列出表 / 表结构 / 数据字典 / 执行 SQL）；没有执行工具时，它只回复一个 ```` ```sql ```` 代码块，你把执行结果或报错发回给它，它再作答或修正。
