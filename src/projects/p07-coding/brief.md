## 甲方：开源组织 TinyLibs

> **维护者小组**：我们维护着十几个小而美的 TypeScript 库（`datekit` 日期工具、`cartcalc` 结账计算、`mdlite` Markdown 渲染……），每周都有几十个 issue，三个维护者根本修不过来。我们想要一个**能自己修 issue 的编码 Agent**：读 issue、在仓库里找到问题、改代码、跑测试，最后交给我们 review。

### 需求

1. 输入是一个 GitHub 风格的 issue（复现步骤、期望、实际，有时还附带提交者对原因的**猜测**——经常猜错）。
2. Agent 通过 `repo` 这组原始 API 操作仓库：列文件、读文件、写文件、搜索、运行测试。**给模型什么工具、怎么设计工具、怎么组织循环，都由你决定。**
3. 修复要**最小、正确、不引入回归**：仓库原有的测试必须继续通过。
4. **绝不允许修改测试**来让测试通过——上次一个 bot 把断言改成了期望错误的值，CI 一片绿，结果发版之后炸了。
5. 修改要尽量靠读代码和跑测试来验证，而不是“看起来对”。

### 验收标准

- 核心测试集：模拟模型下的 6 个 issue，通过率达到 80% 拿 ★，全部通过拿 ★★，token 用量也达标拿 ★★★。
- 完整测试集：17 个 issue（3 个仓库），用真实模型跑基准（「运行基准」），看 pass@1 和 pass^k。

### 判定规则（和 SWE-bench 一样）

Agent 结束后，判定器拿仓库的**最终文件**，在一个全新的、隔离的环境里跑两组测试：

- **FAIL_TO_PASS**：这个 issue 对应的**隐藏测试**（Agent 看不到）。修复前它们会失败，修好之后必须全部通过。
- **PASS_TO_PASS**：仓库里**原有的测试**。修复前就是通过的，修复后也必须全部通过——不能顾此失彼。
- 任何 `*.test.ts` 被修改或删除，直接判失败。

两组测试都通过才算解决了这个 issue。判定只看结果，不关心你用了什么架构、调了几次工具。

### 关于模拟模型

模拟模型是一个“有能力但很死板”的编码模型：它知道核心题该怎么修，但**只能通过你给的工具动手，而且只有在代码真正出现在对话里之后才会修改**。它按名字、描述和参数来认工具（读文件 / 搜索 / 列文件 / 编辑 / 运行测试；编辑工具可以是 `old_str`/`new_str` 式的片段替换，也可以是 `path`/`content` 式的整文件写入）。工具缺什么，它就在对应的地方犯错。
